## 2. New security findings in vendored SaaS starter — OPEN-SIGNUP BLOCKERS
- **SEC-01 (critical) — Unauthorized membership management.** `app/(login)/actions.ts`: `removeTeamMember` checks membership existence but **does not enforce owner/admin server-side**, so a regular member can remove a different member in their team, potentially the owner. `inviteTeamMember` also lacks server-side owner authorization, allowing ordinary member to invite an owner. UI disabled buttons are not authorization. Fix: action-specific permission guard, actor membership role from DB, prevent last-owner removal, verify team scope, tests for 403 (or error state).
- **SEC-02 (critical) — Stripe checkout callback silently logs in by checkout session identifier.** `app/api/stripe/checkout/route.ts` GET retrieves `session_id` and then executes `setSession(user[0])` for the user ID in `client_reference_id`, with no proof requester is that user. Exposure/replay of a valid session ID could cause account login without credentials. Do not publish this route before redesign. Fix: checkout callback cannot establish identity; require independent authenticated session and account/team binding; only verified provider webhook may confirm paid status. Validate subscription ownership and idempotency.
- **SEC-03 (high) — Password hash in /api/user response.** `getUser()` in `lib/db/queries.ts` selects complete user record; `app/api/user/route.ts` serializes it. Authenticated user receives `passwordHash`, violating least disclosure. Fix: explicit safe projection `id/name/email/role` (do not expose password hash), reserve private hash access only for auth service.
- **SEC-04 (high) — Incomplete transactional onboarding.** `signUp` in `app/(login)/actions.ts` inserts the user **before** validating invitation; invalid invite leaves an orphan user. User/team/member/logs in separate operations and `setSession` inside parallel DB mutations; partial failure can leave inconsistent state and logged-in orphan. Fix: validate invite before transaction, use atomic DB transaction for user/team/teamMembers/invite state, then set session after commit. Create tenant provisioning via durable state machine separately.
- **SEC-05 (high) — Invitations are not delivered or securely scoped.** `inviteTeamMember` stores an auto-increment numeric ID and returns `Invitation sent successfully` while source says `TODO: Send invitation email`; no invitation expiry or cryptographically unpredictable invite token. Fix: token hash, expiry, one-time claim, verified email, actual send status and rate limiting. Invitation acceptance must re-check team/role and unique member constraint.
- **SEC-06 (high) — No email verification, abuse rate limits or lockout.** Sign-up and sign-in code uses email/password immediately, no verified email state; protect the public-facing registration/login with email verification, per-IP and per-email rate limits, challenge/Turnstile, and audit. Do not assume `middleware.ts` implements those.
- **SEC-07 (high) — Multi-organization context wrong.** `getTeamForUser` and `getUserWithTeam` select first team only, without a selected tenant/team context and scope enforcement. Design user membership and explicit active team selection per request before supporting multi-merchant owners/staff.
- **SEC-08 (high) — Session cookie and auth configuration fail-closed.** `lib/auth/session.ts` creates JWT signing key from `process.env.AUTH_SECRET` at import time; missing secret must stop startup, invalid/expired token handled without 500 and session revocation supported on role/password changes. Passwords must never be reflected in action responses or logs.
- **SEC-09 (high) — Billing integration not production-safe.** `lib/payments/stripe.ts` creates Stripe client from `STRIPE_SECRET_KEY!`; `BASE_URL`, `STRIPE_WEBHOOK_SECRET` also mandatory for real billing. Checkout action trusts posted `priceId` without server-side entitlement allowlist. Subscription update uses `plan?.product as Stripe.Product` without guaranteeing expanded product; likely incorrect `planName`. Keep payment UI behind explicit, off-by-default feature flag in free staging. Fix after legal seller/payment flow design and sandbox credentials.
- **SEC-10 (high) — Schema constraints missing.** `team_members` no uniqueness `(user_id, team_id)`, invitations no expiry and accepted-unique claim/locking; provisioning/domain uniqueness across systems needs canonical IDs and transaction-safe compensation.

## 3. Corrected CI/CD deployment flow (no paid plan)
**G0 — isolate deployment topology and select one project.** Prefer independent commerce Git repository as main when later feasible (legacy `motngum.cafe` repo triggers other Vercel apps); or explicitly configure one new project to deploy branch `commerce-rebuild-2026-10` and ignore irrelevant commits. Avoid coupling staging root `apps/web` to legacy project. Archive/delete duplicate *new, empty* project only after identifying which holds encrypted env and that chosen project is healthy. No changes to legacy project or DNS.
**G1 — secret + database readiness.** Set `POSTGRES_URL` in **the single chosen project** as an encrypted Preview env var; generate/set `AUTH_SECRET`, correct `BASE_URL`, and either explicitly disable billing mode or provide Stripe TEST credentials only. Never fake PSP credentials. Apply Drizzle migrations to the separate preview database after inspecting SQL diff, test table constraints. Neon database is empty as of audit. Avoid production data from existing Neon databases; free quota is shared.
**G2 — public-safe SaaS functionality.** Fix SEC-01..10. Register -> verify email -> create user/team/membership atomically -> login -> select tenant -> role checks -> invite staff via actual verified email token. Separate account roles from merchant store Admin auth. Implement integration readiness route with 503 until backend, not an artificial "success".
**G3 — merchant provisioning.** Control Plane writes merchant object in PostgreSQL with `requested/provisioning/ready/failed/suspended`, generates canonical merchant ID. Trusted service authentication invokes Cloudflare D1 registry mutation; reserve slug and add domain, map `merchant_id` to Medusa backend; transactional inbox/outbox/replay, idempotency and cleanup on failure. Worker `GET/HEAD` currently rejects writes, so any plan claiming merchant creation is false.
**G4 — Medusa hosting truth.** Choose an actually running backend (CI ephemeral is NOT hosting), with PostgreSQL separate from Control Plane, Redis worker topology, secrets, migrations, stable API. No requirement to upgrade during demo if local/temporary sandbox suffices, but don't publish reliable checkout before persistent provider is secured.
**G5 — storefront tenancy + checkout.** Switch fixed DTC Medusa SDK global singleton to request-scoped backend+publishable key from trusted tenant resolver OR use isolated storefront per merchant. Host-only cookies and tenant-aware cache. Two merchant fixture accounts: product->cart->checkout sandbox->reservation->order->fulfillment->return; signed payment callbacks and duplicate delivery.
**G6 — verify evidence and controlled release.** CI: TypeScript, database migration, server action auth tests, two-tenant isolation tests, Playwright E2E, rollback, no default secrets/unsafe billing. Then preview smoke. Only eventually deploy apex after all services ready and all other subdomains separated. HSK/mail/DNS preservation is mandatory.

## 4. Minimum acceptance test matrix
1. Vercel project build logs show `commerce-rebuild-2026-10` and actual `commerce-platform/control-plane` root; no old `main` build.
2. Correct Vercel project has nonempty encrypted `POSTGRES_URL`, properly generated `AUTH_SECRET`, `BASE_URL`; no inherited website credentials; `Stripe` only TEST when feature enabled.

4. Regular merchant staff cannot invite owner or remove other staff; owner cannot remove final owner; tenant A has no access to tenant B.
5. GET `/api/user` never contains `passwordHash`; GET Stripe checkout callback never creates an authenticated user session.
6. Invitations contain unguessable, expiring, one-time token and are sent, not claimed sent when no email send.
7. Cloudflare D1 registry changes only via trusted authenticated provisioning action, never anonymous POST or user-supplied backend URL.
8. Merchant creation in PostgreSQL and D1 either reaches READY and records backend, or FAILED with safe retry; duplicate request never creates duplicate shop.
9. Running Medusa backend health is reachable from Vercel; Redis and Postgres connected; product/order insertions persist.
10. Two merchant orders at last stock unit do not oversell; failed PSP callbacks do not mark paid; refunds reconcile.
11. Production DNS MX/TXT and HSK/portfolio/web subdomains unchanged; Vercel root project remains intact.
